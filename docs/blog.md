# 一个人的 C++ 性能实验：动态负载下，Lazy LIF 迟滞切换观察到 11.3% 提升，以及它的严格边界

> 独立开发者工程记录。本文分享一组可复现的 C++ 实验，不是学术论文，也不声称提出了全新的神经计算范式。

## 为什么研究这个问题

在稀疏连接的 LIF 网络中，每个时间步并不是所有神经元都会收到输入或递归事件。如果仍然无差别地扫描并更新全部神经元，就可能花费大量时间处理当前没有事件的状态。

我想验证一个很朴素的工程假设：能否只更新当前真正受到事件影响的神经元，并在活动率升高时切回全量扫描？如果工作负载会动态变化，能否用带迟滞的切换策略减少来回切换的成本？

这不是“事件驱动一定更快”的预设结论。事件管理、目标去重、时间戳和延迟衰减同样有成本，必须把它们放进完整推理路径测量。

## 比较了哪些实现

实验使用 CSR 稀疏图和 double 精度状态，比较七种策略：

- **FULL**：每一步扫描并更新所有神经元，但递归事件仍通过 CSR 图传播。它不是 Dense-BLAS。
- **LAZY**：只更新收到外部输入或递归事件的目标；未触及神经元的衰减延迟到下一次触及时结算。
- **A50 / A70 / A90**：当前步被触及的不同目标占比达到 50%、70%、90% 时切换到 FULL。
- **H50_70**：触及率达到 70% 进入 FULL，降至 50% 或以下才返回 LAZY。
- **H70_90**：触及率达到 90% 进入 FULL，降至 70% 或以下才返回 LAZY。

这里的触及率不是外部输入活动率。它是在递归事件传播和外部输入合并后，统计当前时间步被触及的不同目标数量，再除以神经元总数。

## 实验怎么做

两组实验都由 C++17 程序直接生成图和输入序列，固定随机种子，并把每个候选策略与 FULL 参考实现对照。

**动态负载组：** N=4096、T=64；连接密度 0.05% 和 0.2%；图种子 11/22，输入种子 101/202；包括低转高、高转低、周期突发和中高负载四种调度。每个进程有 32 个输入配置、7 个候选策略，共 224 组正确性比较。三个独立进程累计 672 组。

**留出验证组：** N=4096、T=128；连接密度 0.2%；使用新图种子 33/44 和新输入种子 303/404；仍覆盖四种负载调度。每个进程有 16 个输入配置、7 个策略，共 112 组比较。三个独立进程累计 336 组。

每种方法先预热一次，再计时七次并取中位数；每轮旋转方法执行顺序。计时包括 CSR 递归事件传播、外部事件注入、目标去重与累积、状态更新和最终状态物化；不包括图构建、输入生成和结果向量分配。因此它是计算内核/rollout 计时，不是完整应用端到端延迟。

## 正确性先于速度

每个候选策略使用完全相同的图和输入序列，与 FULL 参考实现比较：脉冲输出要求逐项一致；每个时间步的电压快照最大绝对误差必须不超过 1e-12。

归档的六份日志中，每个进程的正确性检查均为零失败，最大电压误差为 4.4408920985e-16，没有脉冲输出不一致。

这说明在已测试的参数范围内，Lazy 和自适应路径与参考实现数值一致到设定容差；它不是对任意网络、任意阈值和任意浮点环境的形式化证明。

## 11.3% 是怎么来的

最醒目的结果出现在留出验证组的周期突发负载：H50_70 的平均时间比值为 **0.887023**，换算为约 **11.30%** 的计时区间缩短；四个测试配置中，H50_70 都快于该配置下的最佳固定策略。

但“最佳固定策略”需要解释清楚。对每个配置，先分别计算 FULL 和 LAZY 在三个独立进程中的平均中位数时间，再事后取二者较小值作为参照：

`best_fixed = min(mean(FULL), mean(LAZY))`

然后计算 `mean(H50_70) / best_fixed`，最后对四个周期突发配置的比值取算术平均。

这是一个很强的**事后 oracle 参照**，因为它对每个配置都知道 FULL 和 LAZY 哪个更快。实际部署时，系统不能天然预知这个答案。因此，11.3% 不是“相对一个在线可用的最优固定策略”的保证，也不是跨任务、跨硬件的普遍加速承诺。

## 严格的边界：哪些地方没有赢

同一留出组的中高负载场景中，迟滞策略没有稳定优于最佳固定策略。更早的动态负载组中，周期突发场景的 H50_70 平均比值约为 0.968644，优势比留出组小得多。

当前证据只覆盖一个容器 CPU 环境、有限的连接密度、四种合成负载和少量随机种子。当前实验没有测量能耗、功耗、GPU 表现、内存带宽，也没有把 Dense-BLAS 或 SIMD 稠密基线纳入这两组动态负载日志。

因此我目前只愿意说：在这些特定周期突发配置中，基于触及目标比例的迟滞切换显示出潜力；在中高负载和其他条件下，它可能没有优势。阈值也仍是手工设定，不是经过大范围训练或自动学习得到的。

## 作为独立开发者，我为什么公开这些细节

我没有学术机构背书，也不打算把一个工程探索包装成论文级结论。更实际的目标是公开代码、原始日志、参数、随机种子、校验和和复现脚本，让读者能检查结果从哪里来，也能发现我可能忽略的问题。

项目仓库提供 C++17 源码、三次独立进程的原始日志、编译命令和复现脚本。欢迎复现、质疑计时方法，或提交其他 CPU 和负载条件下的结果。

**项目结论不是“Lazy LIF 必胜”，而是：负载结构会影响计算路径的成本，动态策略值得测量，但它的收益必须连同适用边界一起报告。**

## 再补充一个统计学限定：这不是盲测确认

虽然 T=128 组使用了新图种子、新输入种子和更长序列，但我在这组数据上同时评估了五种自适应候选策略，之后才识别出周期突发场景中 H50_70 的 11.3% 结果。因此它是“新种子复核中的探索性最佳观察”，不是在看数据前就锁定 H50_70 后得到的盲测确认。三次独立进程也重复使用相同随机种子，不能把 4 个周期突发配置乘以 3，宣称有 12 个独立样本。

下一次真正的确认性实验应当先用开发集选定唯一策略和阈值，再冻结代码、参数和分析方法，最后使用此前完全未查看的新图种子、新输入种子及更多配置做一次性评估。若结果不再达到 11.3%，公开报告也应如实更新。
